## Context

上传页 `KinematicsWorkflowPage.vue` 当前在底部挂载 `FutureCameraViewsPanel`，向用户展示正面 / 俯视 / 水下 / 半水下四张"后续扩展机位"卡片；创建任务页 `CreateSessionView.vue` 的步骤说明也承诺了五机位上传。但端到端链路早已是单一侧面视角：后端 `metrics_service.py` 硬性拒绝非 `side` 视角，分析服务只取 `view_type == SIDE`，上传只绑定 `side`。这些"占位"机位不可上传、不参与分析，纯属 roadmap 预告，却让用户误以为需要选择机位。

本次改动把这些"假多机位"UI 全部移除，使上传页成为明确的单一侧面上传流程。

## Goals / Non-Goals

**Goals:**
- 上传页只呈现侧面机位，不再出现任何其他机位的可选入口或"后续扩展"占位区域。
- 创建任务页文案与"单一侧面机位"现实一致，停止过度承诺多机位。
- 顺带消除 `semi_underwater`（半水下）这一前后端不一致条目。

**Non-Goals:**
- 不收窄后端 `view_type` 枚举（保持 SIDE / FRONT / TOP / UNDERWATER / OTHER，便于将来恢复）。
- 不改分析引擎、标注解析、报告等任何后端逻辑。
- 不做"多机位对比分析"等未来能力——本次只做减法。

## Decisions

**决策 1：直接删除 `FutureCameraViewsPanel.vue` 组件，而非只隐藏。**
理由：组件唯一职责就是渲染那四个未来机位卡片，删除后无任何其他调用方（`KinematicsWorkflowPage` 是其唯一使用处）。隐藏（v-if=false）会留下死代码，与"先删除"的诉求相悖。删除更干净、零风险。

**决策 2：不在上传页用 tab / 下拉替换原面板。**
理由：用户明确"不需要在好几个机位的选项卡里选择"。系统当前只认侧面，引入任何机位选择器都是为不存在的能力增加复杂度。保持单一上传口最简。

**决策 3：后端枚举本次不动。**
理由：用户用"先删除"措辞，暗示未来可能恢复；枚举属于数据库 schema，动它需 alembic 迁移、影响面大。保留宽枚举不会造成功能错误（引擎本就只认 side），可逆且零迁移风险。若日后要彻底一致，再加迁移收窄。

**决策 4：文案修正集中在 `CreateSessionView.vue`。**
理由：多机位观感的另一来源是该页步骤说明"侧面、正面、俯视、水下与半水下视频"。将其改为"上传侧面视频（本次仅分析侧面机位）"，并把"多机位视频上传"等措辞统一为侧面上传，使创建与上传两页口径一致。

## Risks / Trade-offs

- **[风险] 将来要恢复多机位时需重建面板** → 缓解：组件很小、逻辑简单，且 `view_type` 枚举已预留 FRONT/TOP/UNDERWATER，恢复成本低；当前优先满足"不困惑"的体验目标。
- **[风险] 其他文件仍引用"多机位"措辞（如导航标签 `multi-camera upload`）** → 缓解：导航标签属平台级命名，不在本次上传页范围内；若用户要求可后续单独处理，本次不扩大范围。
- **[风险] 删除组件后遗漏 import 导致编译报错** → 缓解：tasks 中明确要求同步移除 `KinematicsWorkflowPage.vue` 里的 import 与 `<FutureCameraViewsPanel>` 用法，并由构建校验。

## Migration Plan

- 纯前端删除 + 文案修改，无数据迁移、无后端部署。
- 回滚策略：git revert 对应提交即可恢复面板与文案，后端不受影响。

- 后端 `view_type` 枚举未来是否要收窄为仅 SIDE？（默认保持，待多机位能力重回路线图时再定。）
